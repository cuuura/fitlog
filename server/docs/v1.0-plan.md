# v1.0 서버 계획 (트랙 A)

계약: `contracts/v1.0/` (앱 트랙 초안 + 서버 보완). v0.1~v0.3 계약은 그대로.

## WP와 소유 범위

| WP | 소유 | 범위 | 완료 기준 |
| --- | --- | --- | --- |
| A1 그래프 API (STA-4) | `server/.../stats/` | `GET /v1/exercises/{id}/progress`, `GET /v1/sessions/{id}/comparison`, 필요 인덱스 `V5__v1.sql`(A1 소유, 다른 WP는 A1에 요청), MCP 도구 `get_exercise_progress` 추가 | 규칙별 통합 테스트(워밍업·미완료·삭제 제외, e1rm 1~10회, isPr 엄격 증가, 같은 day 우선→종목 기준 폴백, 남의 세션 404, limit), 1년치(주 4회) 데이터에서 progress 응답 200ms 이하 |
| A2 보안: 호출 제한·Play Integrity | `server/.../security/`, `core/Plugins.kt` 의 설치 한 줄, `auth/AuthRoutes.kt` 의 검증 호출 | Ktor RateLimit(버킷 auth·api·export·mcp, 환경 변수), 429 RATE_LIMITED + Retry-After, X-Forwarded-For는 `TRUST_PROXY=true`일 때만. `IntegrityVerifier` 인터페이스(실제: Google decodeIntegrityToken, 테스트: 가짜), 모드 off/report/enforce, requestHash=SHA-256(idToken 또는 refreshToken) base64url, 패키지명·인증서 다이제스트·PLAY_RECOGNIZED·MEETS_DEVICE_INTEGRITY 확인, 403 INTEGRITY_FAILED | 버킷별 429 테스트, 모드 3종 × (헤더 없음/실패/성공) 테스트, 실제 Google 호출은 단위 테스트(응답 JSON 파싱)까지 |
| A3 운영: 배포·백업·안정화·정책 페이지 | `server/deploy/`, `server/Dockerfile`, `server/.../ops/`, `server/docs/ops.md`, `server/docs/play-store.md` | Dockerfile, docker-compose(postgres·server·caddy HTTPS·backup), 일일 백업(pg_dump -Fc, 일 14·주 8 보관, 선택 원격 업로드), 복구 스크립트·복구 리허설 스크립트, `/health/ready`(DB 확인), X-Request-Id(CallId)·로그 포함, 요청 본문 크기 제한, 종료 시 정리(graceful), JWT_SECRET 32자 검사, `/privacy`·`/account-deletion` HTML(계약 md 렌더링, CONTACT_EMAIL 치환, 보안 헤더), Play 데이터 보안 양식 답안 문서 | 백업→복구 리허설 스크립트가 로컬 Postgres에서 통과, 페이지·헬스·요청 ID 테스트, docker compose config 검증 |

공용 수정(리드): `Application.kt` 라우트 등록, `AppConfig` 필드, `ErrorCode.INTEGRITY_FAILED`, `build.gradle.kts` 의존성.

## 실기기·실서버로 미루는 항목(사용자)
- Play Integrity 실제 판정(서비스 계정, Play Console 연결, 서명 인증서 다이제스트)
- 실제 서버 배포(도메인·HTTPS)와 일일 백업 cron 동작, 원격 백업 저장소
- 스토어 등록(개인정보 처리방침 URL, 데이터 보안 양식, 계정 삭제 URL), CONTACT_EMAIL 값
- 실기기 성능·크래시 점검(앱 트랙)

## 순서
1. 리드가 공용 골격(설정 필드, 에러 코드, 의존성, 빈 라우트) 커밋
2. A1·A2·A3 병렬(Sonnet 3)
3. 리드 검수 → 전체 테스트 → main 푸시 → 앱 트랙 알림
